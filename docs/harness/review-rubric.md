# レビューと合格条件

通常4役割（code、architect、usability、requirements）、criticalタスクは追加のcritical-reviewerが必要。
役割ごとに以下を返す。主観的な点数を合格根拠にしないというCodex側の既存方針を維持する。

```text
reviewer: <役割>
task: <対象ID>
status: PASS | FAIL
criteria:
  - id: <条件ID>
    verdict: PASS | FAIL | N/A
    evidence: <ファイル箇所・実測チェック・実機証拠。N/Aなら非該当理由>
blocking:
  - id: <指摘ID>
    criterion: <条件ID、または横断的制約>
    location: <ファイルと箇所>
    problem: <問題>
    reproduction: <再現または証拠>
    fix: <必要な修正>
followup:
  - <非blockingの残課題と根拠>
summary: <短い総評>
```

- 全条件IDを一度ずつ列挙する。欠落・重複・架空IDは結果不備。requirementsのN/Aは禁止。
- blockingは仕様/条件違反、不正動作、権限・データ保護の問題、未検証の必須条件、失敗隠蔽など。1件でもFAIL。
- 条件FAILがあるのにPASS、blockingがあるのにPASSは矛盾として拒否する。
- 合格にはtasks.jsonの全checks成功、requirementsの全条件PASS、全必要役割PASS、全blockingゼロ、レビュー対象と検証対象の指紋一致が必要。
- メインは実装前後と判定直前の全ソース一覧・SHA-256を比較し、追加・変更・削除（未追跡ファイルを含む）がタスクの許可範囲内で、AGENTS.mdの保護対象に触れないことを確認する。実装者の変更ファイル申告だけでは足りない。範囲外・保護対象の変更は停止して記録し、意図的に解決する。自動ロールバックやユーザーデータ削除はしない。
- 必須の実機証拠と参照した検証ログは `.harness/evidence/<task>/` の一覧・SHA-256をタスク・check・レビューに結び付け、存在と内容を判定直前・再開時に照合する。変更・欠落は検証失効。変動する `.harness/native/<run-id>/` の進行記録は証拠指紋から除く。
- レビュー・診断によるソース変更は認めない。メインは役割終了後にソース指紋を照合し、変化があれば旧検証・レビューを合格根拠にしない。
- 未実行や環境で実行不能な検証は未検証。模擬テストを実機の証拠にしない。
- メインはblockingを根拠とともに集約する。重複統合しても元の指摘IDを保持し、解消を追跡する。
- 証拠に照らして指摘が誤りなら、レビュワーに再判定を依頼する。実装者やメインが勝手に無視しない。
- followupは合格後も残す。今回の条件に影響しない改善を無限のFIXループにしない。

元のcockpitの4観点と反復構造を継承する。元の85点閾値は採用せず、既存のCodex計画どおり条件ごとの実証で判定する。この違いをレビューの省略や受け入れ条件の緩和に使わない。
